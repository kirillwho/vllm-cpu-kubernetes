# vLLM CPU в Kubernetes

Локальное развёртывание OpenAI-совместимого сервиса генерации текста на базе **vLLM 0.27.0** и **Qwen/Qwen2.5-0.5B-Instruct**. Инференс выполняется на CPU. Проект запускается в Minikube через Docker Desktop и Ubuntu в WSL2 на Windows 11.

Модель загружается отдельным init-контейнером в постоянный том. Основной контейнер читает локальные файлы модели, принимает запросы с Bearer-токеном и записывает события обработки без содержимого запросов и ответов.

## Возможности

* Собственные Dockerfile для сервера и отдельного загрузчика модели.
* CPU-сборка vLLM; версии Python-зависимостей, включая транзитивные, зафиксированы в requirements-файлах.
* Базовый Python-образ закреплён digest в `base-image.txt`, версия модели — commit SHA в `model-revision.txt` и ConfigMap.
* Процессы контейнеров работают с UID/GID 10001, без повышения привилегий; корневая файловая система доступна только для чтения.
* PVC сохраняет модель между пересозданиями Pod. При корректном заполненном кэше повторное обращение к Hugging Face не требуется.
* HF-токен и ключ API передаются через Kubernetes Secret; параметры сервера — через ConfigMap.
* Манифесты объединены через Kustomize.
* Есть проверки авторизации, streaming, отмены запроса, приватности логов и нагрузочный тест.

## Подготовка

Все команды ниже выполняются **в терминале Ubuntu**, из корня проекта. Docker Desktop должен быть запущен, а интеграция с Ubuntu включена в Settings → Resources → WSL Integration.

Для входа в Ubuntu из PowerShell:

```powershell
wsl -d Ubuntu-24.04
```

В Ubuntu:

```bash
cd \\\\\\\\\\\\\\\~/vllm-lab
docker version
minikube version
kubectl version --client
```

При клонировании в другую папку используйте её путь вместо `\\\\\\\\\\\\\\\~/vllm-lab`. Нужны Docker, Minikube, kubectl и Python 3. Для сборки и первой загрузки модели необходим интернет.

Образы, кэш сборки, диск Minikube и файлы модели расходуют место на диске, где расположено хранилище Docker/WSL. Общий объём может составлять десятки гигабайт и превышать размер PVC. Перед запуском проверьте свободное место; состояние Docker можно посмотреть через `docker system df`.

## Сборка образов

Для воспроизведения используйте уже сохранённые `requirements.txt`, `requirements-download.txt`, `base-image.txt` и `model-revision.txt`:

```bash
bash scripts/build.sh
```

Ожидаемые локальные образы: `vllm-cpu:local` и `model-download:local`. Скрипт также проверяет версию vLLM и отсутствие CUDA-сборки Torch. В рабочем запуске получено:

```text
0.27.0
torch CUDA build: None
```

Для первоначальной подготовки файлов или осознанного обновления зависимостей и модели:

```bash
bash scripts/lock.sh
bash scripts/build.sh
bash scripts/revision.sh
```

`lock.sh` разрешает зависимости и сохраняет конкретные версии. Для CPU-wheel vLLM 0.27.0 в основном окружении используется совместимый `setuptools==77.0.3`. `revision.sh` запрашивает текущий commit модели у Hugging Face и записывает его в файл и ConfigMap. Повторный запуск этого скрипта может выбрать другую ревизию, поэтому при обычном воспроизведении он не нужен.

Полные требования по версиям сохранены без обязательного режима `--require-hashes`. Это не следует путать с отдельной проверкой SHA-256 файлов скачанной модели. Lock-файлы и файлы с digest/SHA нужно сохранить в репозитории.

## Первый запуск с пустым PVC

1. Убедитесь, что в `k8s/configmap.yaml` указано `CACHE\\\\\\\\\\\\\\\_ONLY: "0"`. В `MODEL\\\\\\\\\\\\\\\_REVISION` должен стоять полный commit SHA из `model-revision.txt`, а не текстовая заглушка.
2. Убедитесь, что `k8s/offline-test.yaml` не включён в ресурсы `k8s/kustomization.yaml`. Запрет сети применяется отдельно после загрузки модели.
3. Запустите кластер и загрузите в него образы:

```bash
minikube start --driver=docker --cpus=6 --memory=8192 --cni=calico
minikube image load vllm-cpu:local
minikube image load model-download:local
bash scripts/create-secrets.sh
kubectl apply -k k8s
kubectl -n llm-lab get pods,pvc
kubectl -n llm-lab rollout status deployment/llm --timeout=1800s
```

При создании Secret скрипт запрашивает HF read token. Для публичной модели можно нажать Enter; доступ без токена может иметь более низкие лимиты загрузки. API-токен генерируется автоматически и сохраняется в `.local/api-token`.

Первый старт может занять время: init-контейнер скачивает модель, после чего основной контейнер загружает её в память. Статус `Init:0/1` на этом этапе сам по себе не означает ошибку. Диагностика:

```bash
kubectl -n llm-lab logs deployment/llm -c download-model -f
kubectl -n llm-lab describe deployment llm
kubectl -n llm-lab get events --sort-by=.lastTimestamp
```

Ожидаемый результат — Pod `1/1 Running`, PVC `Bound` и успешное завершение rollout. Если используется существующий кластер после offline-теста, для новой загрузки потребуется снять именно политику `offline-proof`; удалять PVC для обычного перезапуска не нужно.

## Доступ к API

В отдельном терминале Ubuntu оставьте работающей команду:

```bash
kubectl -n llm-lab port-forward service/llm 8000:8000
```

Во втором терминале, из корня проекта:

```bash
curl -sS -o /dev/null -w 'HTTP %{http\\\\\\\\\\\\\\\_code}\\\\\\\\\\\\\\\\n' http://127.0.0.1:8000/health
python3 scripts/check\\\\\\\\\\\\\\\_api.py
python3 scripts/check\\\\\\\\\\\\\\\_stream.py
```

`/health` доступен без ключа и может возвращать пустое тело при HTTP 200. Для генерации нужен заголовок `Authorization: Bearer <API\\\\\\\\\\\\\\\_TOKEN>`. Поддерживаются маршруты `/v1/chat/completions` и `/v1/completions`; в запросе используется имя `local-instruct`.

Ключ берётся из `.local/api-token`. Проверочные скрипты читают его самостоятельно — вставлять секрет в исходный код не требуется. После пересоздания Pod может понадобиться заново запустить port-forward.

## Логирование и проверки

Аудит фиксирует события `request\\\\\\\\\\\\\\\_started` и `request\\\\\\\\\\\\\\\_finished` с разрешёнными служебными полями: идентификатором запроса, категорией маршрута, статусом и длительностью. Тело запроса и ответ модели не добавляются в аудит. Штатное логирование содержимого запросов/ответов и access log отключены.

Дополнительно launcher фильтрует stdout/stderr дочернего сервера: наружу передаются только разрешённые JSON-события. Обрабатывается служебный префикс vLLM вида `(APIServer pid=...)`. Произвольный текст и traceback подавляются. Это уменьшает риск утечки, но делает диагностику внутренних ошибок менее подробной.

Порядок интеграционной проверки:

```bash
python3 scripts/check\\\\\\\\\\\\\\\_api.py
python3 scripts/check\\\\\\\\\\\\\\\_stream.py
kubectl -n llm-lab logs deployment/llm -c vllm > .local/pod.log
python3 scripts/check\\\\\\\\\\\\\\\_logs.py
```

В выполненном запуске подтверждены:

* HTTP 401 без ключа и с неверным ключом; HTTP 200 с правильным ключом.
* Отклонение некорректного JSON и запроса с превышением контекста.
* Завершение проверки streaming и клиентской отмены.
* `Log privacy checks passed`, в том числе после нагрузочного теста.

Проверка логов ищет тестовые маркеры, ответы и ключ, а также проверяет допустимые поля и наличие событий аудита. Она покрывает выполненные сценарии и не является доказательством отсутствия утечек при любых возможных входных данных. Тестовые ответы сохраняются локально в `.local/`, а не в журнале приложения.

Дополнительные команды для проверки исходного кода и пользователя контейнеров:

```bash
python3 -m unittest discover -s tests -v
kubectl -n llm-lab exec deployment/llm -c vllm -- id
```

## Повторный запуск без Hugging Face

Загрузчик хранит в каталоге модели маркер `.complete.json` с идентификатором репозитория, ревизией и SHA-256 файлов. При повторном старте он проверяет кэш и возвращается до обращения к Hugging Face. Основной контейнер использует пути `/models/model` для модели и токенизатора.

Для воспроизведения проверки сначала успешно загрузите модель. До запрета сети проверьте доступ к внешнему адресу:

```bash
kubectl -n llm-lab exec deployment/llm -c vllm -- python -c 'import socket; socket.create\\\\\\\\\\\\\\\_connection(("1.1.1.1",443),timeout=3).close(); print("OUTBOUND\\\\\\\\\\\\\\\_OK")'
```

Затем установите `CACHE\\\\\\\\\\\\\\\_ONLY: "1"` в `k8s/configmap.yaml` и выполните:

```bash
kubectl apply -k k8s
kubectl apply -f k8s/offline-test.yaml
kubectl -n llm-lab rollout restart deployment/llm
kubectl -n llm-lab rollout status deployment/llm --timeout=1800s
kubectl -n llm-lab logs deployment/llm -c download-model
kubectl -n llm-lab get pods,pvc
```

Ожидается `{"event":"model\\\\\\\\\\\\\\\_cache\\\\\\\\\\\\\\\_hit","network\\\\\\\\\\\\\\\_used":false}`. Снова выполните проверку соединения с `1.1.1.1:443`: при действующем запрете она должна завершиться ошибкой, например `TimeoutError`. Перезапустите port-forward и повторите проверки API, streaming и логов.

В рабочем запуске получены `model\\\\\\\\\\\\\\\_cache\\\\\\\\\\\\\\\_hit`, готовый Pod, таймаут внешнего соединения и успешные проверки API и логов. Для более убедительного подтверждения действия NetworkPolicy следует сохранить результаты соединения **до и после** её применения: один таймаут без исходного успешного соединения не исключает другие причины недоступности адреса.

Политика `offline-proof` запрещает исходящий трафик Pod с меткой `app=llm`; для её исполнения нужен поддерживающий NetworkPolicy CNI. Режим `CACHE\\\\\\\\\\\\\\\_ONLY=1` дополнительно запрещает загрузчику скачивание при отсутствии готового кэша.

Для возврата возможности загрузки снимите политику, установите `CACHE\\\\\\\\\\\\\\\_ONLY: "0"` и примените ConfigMap:

```bash
kubectl -n llm-lab delete networkpolicy offline-proof --ignore-not-found
kubectl apply -k k8s
```

Уже работающий процесс подхватит параметры при следующем пересоздании Pod. Для публикации репозитория исходная конфигурация первого запуска должна содержать `CACHE\\\\\\\\\\\\\\\_ONLY: "0"`.

## Настройки сервера

Базовая конфигурация в `serve.yaml` внутри ConfigMap:

```yaml
model: /models/model
tokenizer: /models/model
served-model-name: local-instruct
host: 0.0.0.0
port: 8000
dtype: float32
max-model-len: 2048
max-num-seqs: 4
max-num-batched-tokens: 2048
enable-chunked-prefill: true
enable-prefix-caching: false
enforce-eager: true
trust-remote-code: false
```

`max-model-len` ограничивает суммарную длину входа и генерации, `max-num-seqs` — число последовательностей, которые сервер обрабатывает одновременно, `max-num-batched-tokens` — бюджет токенов на итерацию планировщика. Chunked prefill позволяет разбивать обработку длинного входа на части. Prefix caching в baseline выключен.

Дополнительно заданы `VLLM\\\\\\\\\\\\\\\_CPU\\\\\\\\\\\\\\\_KVCACHE\\\\\\\\\\\\\\\_SPACE=1`, `OMP\\\\\\\\\\\\\\\_NUM\\\\\\\\\\\\\\\_THREADS=3` и `VLLM\\\\\\\\\\\\\\\_CPU\\\\\\\\\\\\\\\_OMP\\\\\\\\\\\\\\\_THREADS\\\\\\\\\\\\\\\_BIND=nobind`. CPU KV cache — память для состояния attention при генерации; это другой кэш, чем файлы модели на PVC.

Параметры меняются без пересборки образа:

```bash
kubectl apply -k k8s
kubectl -n llm-lab rollout restart deployment/llm
kubectl -n llm-lab rollout status deployment/llm --timeout=1800s
kubectl -n llm-lab exec deployment/llm -c vllm -- cat /config/serve.yaml
```

После изменения ConfigMap нужен перезапуск: сервер не перечитывает все параметры автоматически. Клиентская `concurrency` в benchmark и серверный `max-num-seqs` — разные настройки.

## Нагрузочный тест

Использован `/v1/completions` со streaming, `temperature=0`, `max\\\\\\\\\\\\\\\_tokens=32`, `ignore\\\\\\\\\\\\\\\_eos=true`. Вход строится из повторяемой тестовой фразы: средняя длина короткого входа — 33,5 токена, длинного — 1083,5. Средний выход во всех прогонах — 32 токена. Дробное число входных токенов является средним по запросам.

Для каждого сочетания short/long и клиентской параллельности 1/4 выполнено три повтора по 20 измеряемых запросов. Перед каждым прогоном выполняется один прогревочный запрос, исключённый из метрик. Всего — 240 измеряемых запросов, ошибок нет.

Команды воспроизведения при работающем port-forward:

```bash
mkdir -p results
kubectl -n llm-lab exec deployment/llm -c vllm -- cat /config/serve.yaml > results/baseline-serve.yaml
for repeat in 1 2 3; do
  for kind in short long; do
    for concurrency in 1 4; do
      python3 scripts/benchmark.py \\\\\\\\\\\\\\\\
        --kind "$kind" \\\\\\\\\\\\\\\\
        --concurrency "$concurrency" \\\\\\\\\\\\\\\\
        --requests 20 \\\\\\\\\\\\\\\\
        --max-tokens 32 \\\\\\\\\\\\\\\\
        --output "results/${kind}-c${concurrency}-r${repeat}.json" \\\\\\\\\\\\\\\\
        || break 3
    done
  done
done
python3 scripts/report.py
```

Повторный запуск записывает файлы с теми же именами. Перед другим экспериментом сохраните предыдущие результаты отдельно. Не смешивайте измерения разных серверных конфигураций в одной таблице без явной маркировки.

Метрики:

* **TTFT** — время от начала клиентского HTTP-запроса до первого непустого текстового SSE-фрагмента.
* **Latency** — время до завершения чтения ответа.
* **p50/p95** — медиана и 95-й процентиль внутри одного прогона; применяется линейная интерполяция.
* **req/s** — количество успешных запросов, делённое на полное время прогона.
* **output tok/s** — сумма выходных токенов, делённая на полное время прогона.

Токены берутся из `usage`. Метрики включают клиентский обмен через port-forward и ожидание на сервере. Ожидание задания в очереди клиентского ThreadPool до начала HTTP-запроса не входит в индивидуальные TTFT/latency, но влияет на полное время прогона. Тест поддерживает не более C одновременных запросов; это не модель потока с заданной частотой поступления.

### Выводы

Для коротких запросов медиана throughput по трём повторам выросла с 0,414 до 1,032 req/s при переходе C=1 → C=4, примерно в 2,49 раза. Медиана значений latency p50 при этом выросла с 2,382 до 3,852 с. Параллельность увеличивает общую пропускную способность, но отдельный запрос в этом сценарии завершается медленнее.

Для длинных запросов аналогичные медианы throughput составили 0,374 и 0,862 req/s — рост примерно в 2,30 раза. Медианы значений latency p50 — 2,667 и 4,618 с. Это медианы трёх показателей прогонов, а не процентили объединённой выборки.

Первый `long-c1-r1` заметно медленнее двух следующих: TTFT p50 составил 3,396 с против 0,327 и 0,316 с. Причина не установлена. Возможны эффекты прогрева, состояния CPU или фоновой нагрузки, но собранных измерений недостаточно, чтобы выбрать объяснение. Прогон сохранён в таблице; исключать его без обоснования нельзя. Один прогревочный запрос перед каждым прогоном уже выполнялся.

Эти измерения сравнивают клиентскую параллельность при одной конфигурации сервера. Они не доказывают ускорение от изменения параметров vLLM. По 20 запросам p95 чувствителен к нескольким медленным ответам; для надёжного вывода о хвостах задержки требуется больше наблюдений.

### Направления настройки

Для большого числа коротких запросов имеет смысл отдельно сравнить `max-num-seqs`, бюджет batching и число OpenMP-потоков. Критерий выбора — throughput при допустимых TTFT/latency p95 и отсутствии ошибок или нехватки памяти.

Для небольшого числа длинных запросов следует изучить стоимость обработки входа, chunked prefill и запас CPU KV cache. Увеличение бюджета токенов или памяти не гарантирует ускорения: изменение нужно проверять теми же сценариями на том же оборудовании.

Каждый эксперимент должен менять один параметр, сохранять конфигурацию и иметь отдельные результаты. Эти направления являются планом дальнейших измерений; их ускорение в приведённой таблице не измерялось.

Версию WSL можно получить командой `wsl --version` в PowerShell. Ревизия модели хранится в `model-revision.txt`; фактический конфиг — в `results/baseline-serve.yaml`. Перед публикацией результатов проверьте, что в них нет секретов и лишних локальных сведений.

## Ограничения и безопасность

* Это локальный стенд с одной репликой и стратегией Recreate; во время пересоздания Pod сервис может быть недоступен.
* Сервис доступен через локальный port-forward. Публичная публикация с TLS, Ingress, ограничением частоты запросов и высокой доступностью отдельно не реализована.
* Non-root относится к процессам контейнеров; rootless-режим самого Docker этим не заявляется.
* Kubernetes Secret отделяет ключи от исходников, но сам по себе не гарантирует шифрование хранилища кластера. Каталог `.local/`, токены, веса модели и сырые логи не должны попадать в Git.
* Закреплённые Python-зависимости и digest базового образа улучшают воспроизводимость. Установка системных пакетов через apt без snapshot не обеспечивает побитово одинаковый образ при каждой будущей сборке.
* Результаты относятся к выбранной модели и локальному CPU-стенду; сравнения качества модели, GPU-инференса и производительности других компьютеров не проводились.
